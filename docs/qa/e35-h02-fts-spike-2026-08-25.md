# Spike FTS5 de E35-H02 — 2026-08-25

Este documento registra la elección de la variante FTS5 para el esquema SQLite vNext de
**E35-H02** (`#54`, trazada localmente como **E34-H02 → E35-H02**). La elección estaba delegada por
#52/#54 dentro de la historia; esta nota no abre una decisión de producto ni cierra
`decisiones §14`.

## Pregunta

El esquema no debe mantener `raw`, un cuerpo parseado separado y una tercera copia completa dentro de
FTS. `documents.body` conserva el snapshot Markdown completo y exacto como única copia completa del
contenido en SQLite. Se compararon dos variantes sobre el mismo corpus, ambas con `rowid = doc_id`
explícito en las inserciones y con mantenimiento real de update/delete:

- **contentless (`content=''`, `columnsize=0`)**: no tiene tabla de contenido ni tabla `docsize`; el
  único escritor suministra los valores antiguos al comando especial `delete` antes de actualizar o
  borrar una fila.
- **external-content (`content=documents`, `content_rowid=doc_id`)**: referencia `documents` como
  tabla de contenido para la comparación de footprint.

## Método reproducible

1. Se usó el mismo corpus no vacío de **10.000 documentos** para las dos variantes, con path, título
   derivado, snapshot Markdown completo y exacto y frontmatter no vacío proyectado en
   `frontmatter_text`.
2. Cada variante se creó en una base SQLite independiente con `doc_id INTEGER PRIMARY KEY`; las
   filas se insertaron con el mismo `rowid` que `doc_id` y con los mismos valores indexados.
3. Se consultaron candidatos con una aguja exclusiva del body (`[4201]`), otra exclusiva del
   frontmatter (`[9877]`) y una compartida por los 10.000 documentos (`shared_count=10000`); ambas
   variantes devolvieron los mismos resultados. La consulta de producción proyecta esos IDs mediante
   `JOIN documents d ON d.doc_id = documents_fts.rowid` y después el core confirma la semántica de
   subcadena.
4. Para update se leyó el snapshot antiguo exacto de `documents.body` (junto con path, título y
   frontmatter textual), se ejecutó el comando FTS5 `delete`, se actualizó `documents` y se insertó
   la nueva fila con el mismo `rowid`. Para delete se repitió el `delete` con esos valores antiguos
   antes de eliminar la fila de `documents`; el test verifica que el término antiguo desaparece, el
   nuevo aparece y el término borrado no queda candidato.
5. Se creó `temp.dbstat` sobre `main` y se sumaron los objetos `documents_fts%` (tabla virtual y
   shadow tables) en el mismo punto de medición, en bytes.
6. La prueba de integración inspecciona además el DDL final, foreign keys, el diccionario `fields`,
   el reata de destinos conocidos y la reconstrucción de una cache incompatible.

El spike pequeño versionado que fija el método está en
`crates/lodestar-store/tests/e35_h02_schema_vnext_red.rs`, en
`c5_spike_fts_mismo_corpus_dbstat_y_eleccion_reconciliada`; la corrida de 10k aporta los números
comparables de esta nota.

## Resultados

| Variante | Shadow/FTS atribuible (`dbstat`) | Candidatos | Mantenimiento |
|---|---:|---|---|
| contentless (`content=''`, `columnsize=0`) | **524288 bytes** | body `[4201]`, frontmatter `[9877]`, shared `10000` | delete/update con valores antiguos exactos de `documents` |
| external-content (`content=documents`, `content_rowid=doc_id`) | **651264 bytes** | body `[4201]`, frontmatter `[9877]`, shared `10000` | comparación; contenido externo en `documents` |

`Shadow/FTS atribuible` suma los objetos `documents_fts` y sus shadow tables informados por `dbstat`.
La unidad es el byte y la corrida usa exactamente el test versionado de 10.000 documentos; no es una
medición de WAL/SHM, RSS ni una extrapolación a 100k o 1M documentos.

El desglose exacto de objetos es:

- contentless: `documents_fts=0`, `documents_fts_config=4096`, `documents_fts_data=516096`,
  `documents_fts_idx=4096`;
- external-content: los mismos objetos y `documents_fts_docsize=126976` adicional.

La salida reproducible del test (`-- --nocapture`) es:


## Decisión

Se elige **contentless**: `524288 bytes` frente a `651264 bytes` de external-content sobre el mismo
corpus, con los mismos candidatos y el mismo protocolo funcional de update/delete. La reducción es
`126976 bytes` en el objeto FTS medido. El coste de mantenimiento es explícito, no implícito: antes de
cualquier cambio el único escritor obtiene de `documents` los valores antiguos exactos —en especial
el snapshot completo de `documents.body`— y los entrega a `delete`.

El DDL final queda, por tanto, ligado a IDs:

```sql
CREATE VIRTUAL TABLE documents_fts USING fts5(
  path UNINDEXED, title, body, frontmatter_text,
  content='', columnsize=0
);
```

Contentless no declara `content_rowid`: `rowid` es un valor explícito que el único escritor fija al
`doc_id` de `documents`. Los candidatos de producción vuelven a obtener la ruta mediante:

```sql
SELECT d.path
FROM documents_fts f
JOIN documents d ON d.doc_id = f.rowid
WHERE documents_fts MATCH ?1
ORDER BY d.path;
```

## Limitaciones y alcance

- El corpus de 10k sirve para elegir la variante y no demuestra el objetivo Realista/100k `≤ 2,5×`.
  Ese objetivo permanece no bloqueante y no se convierte en gate en E35-H02.
- `dbstat` informa el coste de la base principal por objeto; WAL/SHM, page cache y RSS se informan
  por separado en el banco cuando corresponda.
- FTS solo genera candidatos. `DocumentStore` y el core leen el snapshot Markdown completo desde
  `documents.body` en el camino cacheado; el Markdown en disco sigue bajo la autoridad canónica y
  SQLite no es la lectura por defecto mientras `decisiones §14` esté abierta.
- Esta elección no implementa rebuild streaming, watcher incremental, cache RAM, autotuning ni la
  conexión de las lecturas de App/MCP. Esas capacidades quedan en las historias posteriores
  (`#55`, `#56`, `#59`, `#62` según el aspecto).
